Feature requests from the Earheart port. Mihai asked me to port Earheart (github.com/cleanunicorn/earheart, an Electron voice-dictation app: global hotkey, record, transcribe locally, paste into the focused app) to a C app on gesso, on Linux, Windows and macOS, and to send you whatever it needs from gesso. The plan is /code/earheart-native/native/plan.md (the table "What gesso needs" has the evidence per item). The app lives in /code/earheart-native/native on branch feat/native-port and will pin gesso by commit URL, so I can only use what is pushed. Design is yours; below is the behaviour wanted, in the order I will need it. Tell me which you will take, which you think belong in the app instead, and the commit to pin as each lands.

Needed first (my milestone M2: tray + hotkey + record + paste, no windows):
1. Global hotkeys on Windows, macOS and Linux X11: register a key combination that fires while another app has focus, replace it, release it, and report a refused registration (already taken) so the app can keep the old one. Earheart holds up to four at once and releases them all while a settings field captures a key. On Wayland I only need a clear "unsupported here" answer; the app falls back to `earheart --toggle` bound to a system shortcut.
2. Send the paste chord (Ctrl+V, Cmd+V on macOS) to whichever app has focus, with a result that distinguishes "sent", "not permitted" (macOS Accessibility not granted) and "no way to do it here". Earheart today spawns PowerShell, osascript and xdotool/wtype/ydotool for this; native calls would drop a process start per dictation and macOS's Automation permission. On Wayland, spawning wtype or ydotool is fine.
3. A probe and prompt for macOS Accessibility permission (is this process trusted; open the system prompt or settings pane).
4. Single instance with argument forwarding: a second `earheart --toggle` hands its arguments to the running instance and exits.
5. macOS app bundles from the Zig build: Info.plist with usage strings (NSMicrophoneUsageDescription), an icon, a tray-only mode with no Dock icon (LSUIElement), and signing with a named certificate. A bare executable cannot ask for the microphone. Evidence that macOS builds work at all: on a rented Mac mini (M2 Pro, macOS 26.6.2, Xcode 26.5, Zig 0.17.0) gesso at 521ce3a passes `zig build test` with and without -Dvideo, and gtube v0.2.1 builds and renders `--demo --shot`. castholm/SDL refuses to cross-compile to macOS without SDK paths, so macOS builds must run on a Mac or a macOS CI runner. Ask Mihai for access to that machine if you want it.
6. Writing JSON (gs_json only reads): settings and history are JSON files, written whole and atomically.

Needed next (M4 overlay, M5 settings/wizard):
7. A window that never takes keyboard focus, stays above other windows including full-screen apps, shows on every workspace, and is transparent. SDL has the flags for most of it; all-workspaces and above-full-screen have no SDL call, and native Wayland cannot place a window.
8. Several windows in one process, each with its own gs_ui (overlay, settings, wizard and a correction editor can be open together).
9. Drawing for a designed interface: rounded rectangles (filled and outlined), per-draw opacity, a progress bar, and a way to animate (ease a value over time and keep frames coming while it moves).
10. Form controls gs_ui lacks: a masked field for API keys, a radio group, a number field, a clickable link, a long page of sections with a scroll position the app can read and set (for an index that follows the scroll), and a modal confirm.
11. Every control reachable with Tab/Shift+Tab and operable from the keyboard with a visible focus mark. This is a stated product commitment of Earheart's.
12. A field that captures a key combination (for choosing a hotkey) and reports it in a form the hotkey module accepts.

Later (after M5, lower priority): desktop notifications whose click reaches the app (gsignal's roadmap wants these too), macOS Keychain and Linux Secret Service storage in gs_secret, start on login.

I will take SDL's tray, microphone capture and clipboard MIME types directly from SDL. If any of 1 to 6 will take you more than a day or two, say so and I will write a stopgap in the app.

Update, 2026-10-11, after building M2 (tray + hotkey + record + paste) on all three systems.

Items 1 to 4 now exist in the app as stopgaps you are welcome to lift, each tested end to end (Linux under Xvfb and Windows in CI, macOS on the rented Mac with the real hotkey and a paste into TextEdit):
- native/src/desk.h is the interface; desk.c parses Electron-style accelerators.
- desk_linux.c: X11 key grabs on a connection of its own with libX11 opened at run time (four grabs per hotkey for Caps Lock and Num Lock, refusal detected through the X error handler), and the paste keystroke through wtype, ydotool or xdotool as the Electron build does it.
- desk_windows.c: RegisterHotKey on a thread with its own message queue, SendInput for Ctrl+V, a named pipe for the one instance.
- desk_macos.c: Carbon RegisterEventHotKey (no permission needed), a posted Cmd+V after AXIsProcessTrusted, and AXIsProcessTrustedWithOptions to raise the system's prompt. desk_unix.c: the instance socket.
- item 5: native/tools/bundle-macos.sh makes the .app (Info.plist with the microphone string and LSUIElement, icon set, signing). SDL also needs SDL_HINT_MAC_BACKGROUND_APP set or the app shows in the Dock.

Three findings that are gesso or SDL matters:
13. Clipboard snapshot and restore. SDL_GetClipboardMimeTypes lists nothing for another app's contents on macOS, so a snapshot through SDL came back empty there and the user's clipboard was lost after a paste. The app now uses NSPasteboard items (desk_macos_clipboard.m) and, on Windows, every memory-backed clipboard format (desk_windows.c); Linux keeps SDL's formats.
14. The tray on Linux. SDL_CreateTray fails with "Could not load AppIndicator libraries" where libayatana-appindicator is not installed (this Fedora host; GNOME also needs an extension to show any tray). Electron's tray speaks the StatusNotifierItem protocol over D-Bus itself. A tray that does the same without the library would make the tray work on more desktops.
15. SDL_GetTrayEntries returns SDL's own array, which shifts under SDL_RemoveTrayEntry; removing entries while walking it crashed on macOS. Not a bug, but worth a note for whoever wraps the tray.

Still wanted from you, in this order: item 6 (JSON writing; the app has src/jv.c meanwhile), then 7 to 12 for the overlay and the settings window, which I will start on next. If you would rather I keep building what I need in the app and hand you finished pieces, say so.

Update, 2026-10-11, after building M4 (the overlay) in the app.

The overlay exists and runs on Linux and macOS: native/src/overlay.c (the card, its state and its window) on native/src/draw.c (rounded rectangles filled and outlined, circles, thick lines and triangles through SDL_RenderGeometry with a one-pixel fading rim). Lift or replace either. The window is made with SDL_WINDOW_BORDERLESS, TRANSPARENT, ALWAYS_ON_TOP, UTILITY, NOT_FOCUSABLE and HIGH_PIXEL_DENSITY, and on the Mac a paste lands in TextEdit while it is showing.

Findings:
16. On an X display with no window manager SDL's X11_ShowWindow calls XSetInputFocus on every window it shows, NOT_FOCUSABLE or not, so the overlay took the keyboard under a bare Xvfb. Under a window manager it does not. Tests that check focus need a window manager (the app's CI starts Openbox).
17. Font weights and a monospace face. gs_fontset_system gives one regular face. The overlay's design sets the status in semibold and the timer in the system's monospace face with tabular digits; the settings window will want semibold headings. Wanted: the system font in a chosen weight (400, 500, 600) and the system monospace face.
18. Tooltips: a short text shown after the pointer rests on a control. The overlay's keys name their hotkeys that way, and a detail line cut at two lines shows its full text.
19. gs_fontset_wrap with a limit of lines and an ellipsis on the last would replace what the overlay does by hand for its two-line detail.

Update, 2026-10-12, after building M5 (settings, wizard, correction editor) in the app.

The three windows are built on native/src/ui.c, a layer over gs_ui that is yours to lift: a Tab order with a focus mark and Space/Enter activation, one scrolling page per window with a glide, rounded buttons, switches, radio buttons, a slider with stops, a field that captures a key combination as an Electron accelerator, a modal question, and controls that are shown and cannot be used. native/src/window_smoke.c drives real windows with synthetic SDL events and is a pattern you may want for gs_ui's own tests.

What I had to work around in gs_ui, in the order it cost me:
20. No way to read a text area's selection (start and end). The correction editor needed "what is selected" and I replaced selecting with picking words.
21. gs_ui's controls know nothing of a clip or of being disabled, so a field half under a scrolling page's edge still takes clicks there. The layer draws a still look-alike whenever the pointer is outside the page or the controls are inert. A disabled state and hit testing that respects gs_ui_clip would remove that.
22. A field empties itself on Escape. Right for a search box, wrong for a settings field; the layer keeps Escape from reaching gs_ui.
23. No masked field. The layer shows dots unless the field has the keyboard.
24. Fields, text areas and dropdowns are square; a corner radius in gs_ui_style would let them match rounded controls.
25. gs_http has no way to read response headers, which a resumed download needs to compare ETag or Last-Modified when a file has no checksum.
26. Nothing redraws after an input unless the pointer moves, since effects of a click show on the next frame. The layer asks for one more frame after every input; gs_ui_wait_ms could return 0 after a frame that consumed input.

Update, 2026-10-12, after moving onto gesso 341834b.

The app now uses gs_ui's controls (src/ui.c is the window, the colours, the button kinds and a list of controls for tests), gs_desk, gs_overlay_window, gs_draw, gs_jval and the weighted and monospace fonts. Its own jv.c, draw.c and desk*.c are gone. Items 1 to 12, 17, 19 to 24 and 26 are answered by that. What did not fit or is still wanted:
27. tools/ is not in gesso's build.zig.zon paths, so tools/bundle-macos.sh is not in the fetched package and b.dependency("gesso", .{}).path("tools/bundle-macos.sh") finds nothing. The app keeps its own script.
28. gs_desk has no call to bring the app forward. On macOS an app without a Dock icon is not made active by showing a window, so a settings window opens without the keyboard; the app calls [NSApp activateIgnoringOtherApps:YES] itself (src/activate_macos.m).
29. A text area inside a page takes the wheel while the pointer is over it even when it cannot scroll (short text, or already at its end), so a settings page stops scrolling when the pointer reaches the dictionary box. Passing the wheel on when the inner control has nowhere to go would match what browsers do.
30. gs_ui_confirm's two buttons cannot be clicked by a test that looks controls up by name; the app's tests answer with the keyboard. A way to ask where a named control is would let tests of any gs_ui app click things.


Update, 2026-10-12, on gesso b9d72d9: items 27 to 30 are answered and in use. `zig build bundle -Didentity="Earheart Dev"` runs gesso's bundle script from the package and the result is signed and launches on the Mac; the settings window comes forward as the key window through gs_window_activate on the Mac's screen (macOS 26); the settings test turns the wheel over the dictionary box and the page moves. gs_ui_where is not used yet: the app's tests still keep their own list of controls, because they also ask how many there are and which are on the page.
